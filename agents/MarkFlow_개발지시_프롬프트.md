# MarkFlow 개발 지시 프롬프트 (Antigravity IDE용)

문서 → Markdown 변환·클라우드 연결·내보내기에서 출발해, DEVONthink형 종합 문서·개인 지식 관리 앱(mac/Windows, Things 스타일 UI)까지 Antigravity 에이전트가 11단계로 만들도록 지시하는 프롬프트 모음

---

## 0. 사용법 (사람이 하는 일)

### 0-1. 핵심 구조
- 규칙 파일 1개 + 단계별 프롬프트 11개로 구성함
  · 규칙 파일(`markflow-rules.md`): 에이전트가 **매번 자동으로 읽는 헌법**. 기술 스택·폴더 구조·보안 원칙이 들어 있음
  · 단계별 프롬프트(Phase 0~10): 하나씩 **복사 → 에이전트 입력창에 붙여넣기** 하는 작업 지시서
- 한 Phase가 끝나고 "완료 기준"을 직접 확인한 다음에만 다음 Phase로 넘어감
  ※ 한꺼번에 다 시키면 에이전트가 중간에 길을 잃고 품질이 급격히 떨어짐

### 0-2. 준비 순서
1. 맥미니(또는 맥북)에 빈 폴더 `markflow`를 만들고 Antigravity에서 **Open Folder**로 엶
2. 폴더 안에 `.agents/rules/` 폴더를 만들고 `markflow-rules.md`를 넣음
   ※ Antigravity는 `.agents/rules/` 안의 파일을 워크스페이스 규칙(Workspace Rule)으로 인식함. 파일당 12,000자 제한이 있으며 이 파일은 그 안에 맞춰 작성됨
3. 이 문서도 `docs/MarkFlow_개발지시_프롬프트.md`로 넣어 둠 (에이전트가 전체 그림을 참조하게 함)
4. 에이전트 설정
   · 모드: **Planning** (계획 먼저 → 승인 → 구현). Fast 모드는 쓰지 않음
   · 모델: 목록 중 가장 상위 모델 선택
   · Review Policy: **Request Review** (계획·큰 변경 시 사용자 승인 요청)
   · 터미널 명령 자동 실행: "Auto"는 허용하되 삭제(`rm`, `del`) 명령은 확인 받기
5. 테스트용 샘플 문서 10~20개를 `samples/` 폴더에 넣음
   · 권장 구성: DOCX 3, PPTX 3, XLSX 2, PDF(텍스트) 3, PDF(스캔본) 2, HTML 2, 이미지(PNG·JPG, 글자 포함) 3
   · ⚠ 회사 기밀 문서는 넣지 않음 — Phase 3에서 무료 LLM(외부 서버)으로 보낼 수 있기 때문

### 0-3. 용어 풀이 (프롬프트에 나오는 말)
| 용어 | 쉬운 뜻 |
|---|---|
| Electron | 웹 화면 기술(HTML·React)로 윈도우·맥 앱을 동시에 만드는 틀. VS Code·Slack이 이걸로 만들어짐 |
| 사이드카(Sidecar) | 앱 옆에 붙어 같이 실행되는 보조 프로그램. 여기서는 MarkItDown(파이썬)을 돌리는 변환 엔진 |
| FastAPI | 파이썬 프로그램에 "주문 창구(API)"를 달아주는 도구. 화면이 "이 파일 변환해줘"라고 요청하면 엔진이 응답함 |
| MarkItDown | Microsoft가 공개한 문서→Markdown 변환 라이브러리 |
| 플러그인 | 기본 기능에 덧붙이는 확장 부품. `markitdown-ocr`은 문서 속 이미지의 글자를 읽어주는 확장 |
| OCR | 이미지 안의 글자를 텍스트로 읽어내는 기술 |
| frontmatter | MD 파일 맨 위 `---` 사이에 넣는 속성 정보(제목·태그·상태). 노션의 "속성" 칸에 해당 |
| 골든셋(Golden set) | "이 파일은 이렇게 변환돼야 정답"이라고 정해둔 기준 샘플. 품질이 나빠졌는지 자동 검사하는 데 씀 |
| 키체인(Keychain) | OS가 제공하는 비밀번호 금고. GitHub 토큰을 여기에 암호화해 보관 |
| PAT | GitHub Personal Access Token. 앱이 내 대신 GitHub에 파일을 올릴 수 있게 하는 출입증 |
| 커밋(Commit) | 코드 변경을 "저장 시점"으로 기록하는 것. 문제가 생기면 그 시점으로 되돌릴 수 있음 |
| 동기화 폴더 | Google Drive·OneDrive·Dropbox·iCloud 앱을 깔면 PC에 생기는 폴더. 여기 넣은 파일이 자동으로 클라우드에 올라감 |
| 온라인 전용 파일 | 클라우드에만 있고 PC에는 이름만 보이는 파일(구름 아이콘). 열면 그때 내려받아짐 |
| OAuth | "구글로 로그인"처럼 비밀번호를 앱에 주지 않고 권한만 빌려주는 로그인 방식 |
| 감시 폴더 | 지정해 두면 새 파일이 들어올 때마다 앱이 알아서 변환하는 폴더 |
| 임베딩 | 글의 의미를 숫자 묶음으로 바꾼 것. 숫자가 비슷하면 내용도 비슷하다고 판단해 관련 문서를 찾아줌 |
| 스마트 그룹 | 검색 조건을 저장해 두면 조건에 맞는 문서가 자동으로 모이는 그룹 |
| 디자인 토큰 | 색·글꼴 크기·간격 같은 디자인 값을 이름 붙여 한곳에 모아둔 것. 바꾸면 앱 전체에 한 번에 반영됨 |
| GitHub Actions | GitHub가 제공하는 무료 자동 빌드 서버. 맥·윈도우용 설치 파일을 각각 만들어 줌 |

### 0-4. 문제가 생겼을 때 쓰는 공통 프롬프트
- 에러가 났을 때
  ```
  방금 에러가 났어. 에러 메시지 전체를 읽고 (1) 원인을 쉬운 말로 설명하고 (2) 고친 뒤 (3) 같은 테스트를 다시 돌려서 통과하는 걸 보여줘. 추측으로 고치지 말고 원인을 확인한 다음 고쳐.
  ```
- 결과가 마음에 안 들 때
  ```
  [파일명] 변환 결과에서 [구체적 문제: 예) 표가 깨짐 / 제목 단계가 사라짐 / 이미지 글자가 안 나옴]이 있어. 원본과 결과를 비교해서 원인을 찾고, 골든셋 테스트에 이 사례를 추가한 다음 고쳐줘.
  ```
- 에이전트가 엉뚱한 방향으로 갈 때
  ```
  멈춰. markflow-rules.md와 현재 Phase 지시서를 다시 읽고, 지금 하고 있는 작업이 그 범위 안인지 확인해. 범위 밖이면 되돌리고 계획부터 다시 보여줘.
  ```
- 대화가 길어져 맥락이 흐려질 때: 새 대화(New Conversation)를 열고 아래를 붙여넣기
  ```
  docs/MarkFlow_개발지시_프롬프트.md와 docs/walkthrough/ 폴더를 읽고 지금까지 진행 상황을 요약해줘. 그다음 Phase [N]을 이어서 진행하자.
  ```

## Phase 0. 개발 환경 점검

**목적:** 맥에서 개발에 필요한 도구가 다 깔려 있는지 확인·설치함

```
[Phase 0 — 개발 환경 점검]

markflow-rules.md를 먼저 읽어줘. 이 프로젝트는 그 규칙을 따른다.

이번 Phase에서는 코드를 만들지 말고 개발 환경만 점검·준비해.

Windows에서도 나중에 같은 환경이 필요하니, Windows용 설치 명령(winget)도 phase-0.md 끝에 따로 적어줘.
```

**완료 기준 (직접 확인)**

## Phase 1. 뼈대 만들기 + 앱↔엔진 연결

**목적:** 빈 화면의 앱이 뜨고, 앱이 파이썬 변환 엔진을 자동으로 켜서 "살아있는지" 확인하는 단계까지

```
[Phase 1 — 프로젝트 뼈대 + 사이드카 연결]

markflow-rules.md의 기술 스택과 폴더 구조를 그대로 따라 프로젝트 뼈대를 만들어.

구현 범위
1. apps/desktop: electron-vite + React + TypeScript + Tailwind + shadcn/ui 초기 구성
2. engine: uv로 Python 3.12 프로젝트 생성, FastAPI 앱에 GET /health (엔진 버전, markitdown 버전 반환)
3. Electron 메인 프로세스가 앱 시작 시
   - 비어 있는 포트를 찾아 Python 엔진을 자식 프로세스로 실행 (개발 중에는 uv run, 배포 시에는 PyInstaller 실행파일 — 둘 다 고려한 구조로)
   - /health 가 응답할 때까지 최대 15초 대기, 실패 시 화면에 원인과 함께 오류 표시
   - 앱 종료 시 엔진 프로세스를 확실히 종료 (Windows에서 좀비 프로세스가 남지 않게)
   - 엔진이 비정상 종료되면 1회 자동 재시작
4. 화면: markflow-rules.md 8장(Things 스타일)대로 앱 뼈대 화면을 만들어
   - 왼쪽 사이드바(수집함·오늘·검토 필요·라이브러리·기록 자리, 아직 빈 화면) + 오른쪽 본문
   - 디자인 토큰(색·글꼴·간격·모서리·그림자·애니메이션 시간)을 한 파일로 정의하고 docs/design-system.md에 정리, 라이트/다크 모드
   - 엔진 상태는 사이드바 맨 아래 작은 점(초록/빨강)으로만, 마우스를 올리면 markitdown 버전 표시
   - docs/ui-checklist.md(8장 원칙을 점검 항목으로 바꾼 것)도 이때 만들어
5. 루트에 개발 실행 명령 하나로 앱+엔진이 같이 뜨게 (pnpm dev)
6. 테스트: engine에 pytest로 /health 테스트, desktop에 vitest 기본 테스트 1개

구현 전에 Implementation Plan(파일 목록, 사이드카 실행·종료 방식, 포트 선택 방식)을 먼저 보여줘.
끝나면 rules의 Phase 종료 절차(테스트 → 앱 실행 스크린샷 → walkthrough → 커밋)를 수행해.
```

**완료 기준**
- `pnpm dev` 한 번으로 앱 창이 뜨고, 왼쪽 사이드바 + 오른쪽 본문의 깔끔한 빈 화면이 보이며 사이드바 아래 점이 초록색임
- 앱을 닫은 뒤 활동 모니터에서 python 프로세스가 남아 있지 않음

## Phase 2. 변환 v1 + 좌우 화면 (드래그 앤 드롭 / 변환 내역)

**목적:** 요구사항의 핵심 화면 완성. 왼쪽에 파일을 떨어뜨리면 변환되고 오른쪽에 결과 내역이 쌓임

```
[Phase 2 — 기본 변환 + 좌우 2분할 화면]

1. 엔진 API
   - POST /convert : 파일 경로를 받아 MarkItDown 기본 설정으로 변환, 결과 MD 텍스트와 메타정보 반환
   - 지원 확장자: docx, pptx, xlsx, xls, pdf, html, htm, png, jpg, jpeg, webp, csv, txt, json, xml, zip
   - 지원하지 않는 확장자(예: hwp)는 "미지원" 상태로 명확히 반환
   - 변환 결과는 markflow-rules.md 5장 규칙대로 Library/<slug>.md 로 저장 (frontmatter 포함). slug는 한글 파일명을 유지하되 OS 금지문자만 치환, 중복이면 -2, -3 붙임

2. 화면 레이아웃 — 이 화면은 사이드바 [수집함]의 본문이다. rules 8장 원칙 준수
   (본문을 가로 2분할, 가운데 경계선 드래그로 폭 조절)
   - 왼쪽 "변환 대기열"
     · 큰 드롭 영역: 파일·폴더 드래그 앤 드롭, 클릭 시 파일 선택 창. 폴더를 넣으면 하위 지원 파일을 모두 추가
     · 대기열 목록: 파일명, 형식 아이콘, 크기, 상태(대기/변환중/완료/실패/미지원), 개별 삭제·재시도 버튼
     · 하단 버튼: [전체 변환], [대기열 비우기]. 옵션: "넣자마자 자동 변환" 토글
     · 동시에 최대 2개씩 변환(엔진 과부하 방지), 진행 상태 실시간 표시
   - 오른쪽 "변환 내역"
     · 목록: 제목, 원본 형식, 변환 일시, 품질점수(이번 Phase는 비워 둠), 내보내기 상태 배지
     · 검색창(제목·파일명), 정렬(최신순/이름순)
     · 항목 클릭 시 아래쪽(또는 우측 패널)에 MD 미리보기(렌더링된 화면)
     · 항목 우클릭/메뉴: Finder(탐색기)에서 보기, MD 복사, 삭제(휴지통으로 이동 + 되돌리기 토스트, 확인 창 없음)
   - 변환 이력은 SQLite에 저장해 앱을 다시 켜도 유지

3. 실패 처리: 실패 시 오류 원인을 사람이 이해할 수 있는 한국어로 표시 (예: "암호가 걸린 PDF입니다")

4. 테스트: samples/ 폴더의 모든 파일을 엔진으로 일괄 변환하는 pytest 작성 — 크래시 0건, 변환 결과 비어 있지 않음을 검증

Implementation Plan과 함께 화면 와이어프레임(간단한 텍스트 또는 이미지)을 먼저 보여줘.
```

**완료 기준**

- 앱을 껐다 켜도 내역이 남아 있음
- Library 폴더에 frontmatter가 붙은 `.md` 파일이 생김

## Phase 3. 변환 품질 극대화 (이 앱의 핵심 경쟁력)

**목적:** MarkItDown 기본 변환의 약점(이미지 속 글자 누락, 스캔 PDF, 표 깨짐, 웹페이지 잡음)을 보완해 품질을 최대로 끌어올림

```
[Phase 3 — 변환 품질 파이프라인]

MarkItDown을 핵심 엔진으로 유지하면서, 앞뒤에 전처리·후처리를 붙여 품질을 최대화해.
파이프라인: preprocess → convert(MarkItDown) → enrich(OCR/LLM) → postprocess → quality(점수)
라이브러리 API는 추측하지 말고 설치된 markitdown·markitdown-ocr 소스를 직접 읽고 확인한 뒤 구현해.

1. 형식별 전처리 (preprocess)
   - HTML: readability-lxml로 본문만 추출(메뉴·광고·푸터 제거) 후 변환. 원문 URL을 알 수 있으면 frontmatter에 source_url
   - PDF: 페이지별로 텍스트 추출 가능 여부 판단 → 텍스트 없는 페이지는 "스캔 페이지"로 표시해 OCR 대상으로
   - 암호 PDF·손상 파일은 사전 감지해 친절한 오류로

2. 이미지 보존 (MarkItDown 기본값은 문서 속 이미지를 버림)
   - keep_data_uris 옵션 등으로 DOCX·PPTX의 내장 이미지를 받아, base64 데이터를 Library/assets/<slug>/img-001.png 파일로 저장하고 MD 링크를 상대경로로 교체
   - PDF 내장 이미지는 pypdfium2 또는 pdfplumber로 추출해 같은 방식 처리
   - 아주 작은 이미지(아이콘·로고, 예: 64px 미만)는 제외

3. OCR·이미지 설명 (enrich) — markitdown-ocr 플러그인 사용
   - MarkItDown(enable_plugins=True, llm_client=..., llm_model=...) 구조로 연결
   - llm_client는 OpenAI 호환 클라이언트. 공급자 프리셋 2개:
     · Gemini 무료 API (OpenAI 호환 엔드포인트 https://generativelanguage.googleapis.com/v1beta/openai/) — 모델명은 설정값으로, 현재 무료로 쓸 수 있는 Flash 계열을 기본값으로 하되 실제 사용 가능 여부를 확인해
     · 로컬 LLM (http://localhost:1234/v1, LM Studio 호환)
   - 한국어 문서 기준 프롬프트로 교체: "이미지 속 글자를 빠짐없이 원문 그대로 추출하고, 표는 Markdown 표로, 도식은 구조를 글머리표로 설명"
   - 무료 한도 초과(429) 시: 지수 백오프로 재시도 → 그래도 실패하면 해당 이미지만 건너뛰고 변환은 계속, 결과에 "OCR 일부 누락" 표시
   - LLM 기능은 기본 OFF. 켤 때 외부 전송 경고 표시(rules 6장)
   - Azure Document Intelligence(docintel_endpoint) 경로도 코드에 넣되 기본 OFF, 설정에서만 켤 수 있게

4. 후처리 (postprocess)
   - PDF 특유의 문장 중간 줄바꿈 이어붙이기(한국어 문장 기준), 하이픈 단어 분리 복원
   - 반복되는 머리글·바닥글·페이지 번호 줄 제거
   - 제목 단계(#, ##, ###) 정리: 1단계 제목이 여러 개거나 단계가 건너뛰면 보정
   - PPTX: 슬라이드마다 "## 슬라이드 N. 제목" 구조, 발표자 노트는 "> 노트:" 인용으로
   - XLSX: 시트마다 "## 시트명" + 표. 빈 행·열 제거, 너무 큰 시트(예: 500행 초과)는 앞부분 + "이하 생략(전체 N행)" 옵션
   - 연속 빈 줄 2개 이상 → 1개, 표 정렬 보정, 깨진 문자(�) 감지

5. 품질 점수 (quality, 0~100)
   - 지표 예: 원본 대비 추출 글자 비율, 깨진 문자 비율, 표 개수 보존, 이미지 처리율, 스캔 페이지 OCR 성공률
   - 70점 미만은 status를 "검토중"으로 두고 내역 화면에 노란 배지
   - 점수 산식은 docs/quality-score.md에 쉬운 말로 기록

6. 변환 프로필 (설정 화면에서 선택)
   - 빠름: MarkItDown 기본만
   - 균형(기본값): 전처리 + 이미지 보존 + 후처리 + 점수
   - 최고 품질: 균형 + OCR/LLM 설명
   - 문서별로 프로필을 바꿔 재변환 가능

7. 골든셋 회귀 테스트
   - engine/tests/golden/ 에 samples/ 중 대표 파일과 "기대 결과 체크 항목"(반드시 포함돼야 할 문장, 표 개수, 제목 수)을 정의
   - pytest로 매번 검사해 품질이 떨어지면 테스트가 실패하게
   - 기본 MarkItDown 대비 개선 결과를 파일별 비교표로 docs/walkthrough/phase-3.md에 정리 (점수 전/후)

Implementation Plan에 "형식별로 무엇이 개선되는지" 표를 포함해서 먼저 보여줘.
```

**완료 기준**
- phase-3.md 비교표에서 대부분 파일의 품질점수가 기본 대비 올라감
- 글자가 들어간 PNG와 스캔 PDF를 "최고 품질"로 변환하면 글자가 MD에 나옴
- DOCX·PPTX 변환 결과에서 이미지가 `assets/` 폴더에 저장되고 미리보기에 보임

## Phase 4. 미리보기·원본 비교·편집

**목적:** 변환 결과를 원본과 나란히 보고 바로 고칠 수 있게 함

```
[Phase 4 — 상세 보기 · 비교 · 편집]

1. 변환 내역에서 문서를 열면 상세 화면 (탭 3개)

4. 단축키: Cmd/Ctrl+S 저장, Cmd/Ctrl+F 문서 내 검색
```

## Phase 5. 내보내기 — GitHub LLM-wiki / iCloud Obsidian

**목적:** 변환된 MD를 버튼 하나로 내 지식 저장소 두 곳에 올림

```
[Phase 5 — 내보내기]

1. 설정 화면 > 내보내기 대상
   - GitHub: 저장소(기본값 innohood-lab/LLM-wiki), 브랜치(main), 대상 폴더(기본값 inbox/markflow/), PAT 입력
     · PAT는 safeStorage로 암호화 저장. 화면에는 앞 4자리만 표시
     · [연결 테스트] 버튼: 저장소 접근 권한 확인
     · PAT 발급 방법(Fine-grained token, 해당 저장소만, Contents: Read and write 권한)을 설정 화면 도움말에 단계별로
   - Obsidian: 볼트 폴더 경로 선택(폴더 선택 창), 대상 하위 폴더(기본값 00_Inbox/MarkFlow), 첨부 폴더(기본값 attachments/MarkFlow)
     · 경로 힌트 표시: mac `~/Library/Mobile Documents/iCloud~md~obsidian/Documents/<볼트명>`, Windows `iCloudDrive\iCloud~md~obsidian\<볼트명>` (iCloud for Windows 설치 필요)
     · 볼트 폴더 안에 .obsidian 폴더가 있는지 검사해 잘못된 경로를 막음

2. GitHub 업로드 방식
   - git 설치 없이도 동작하도록 GitHub REST API(Octokit) 사용
   - 여러 문서를 한 번에 올릴 때는 Git Data API(tree → commit → ref 갱신)로 "커밋 1개"로 묶음. 커밋 메시지: "markflow: N개 문서 추가 (날짜)"
   - MD와 해당 assets 이미지를 함께 업로드, 링크 경로가 저장소 안에서도 깨지지 않게
   - 같은 경로 파일이 이미 있으면: 내용이 같으면 건너뜀 / 다르면 [덮어쓰기 · 이름 바꿔 올리기 · 건너뛰기] 선택
   - 실패 시 원인(권한·네트워크·충돌)을 한국어로 표시하고 재시도 가능

3. Obsidian 내보내기 방식
   - 볼트 폴더로 파일 복사(MD + 이미지). 이미지 링크를 볼트의 첨부 폴더 기준 상대경로로 다시 계산
   - frontmatter의 tags는 Obsidian 태그 형식과 호환되게 유지

4. 화면 연결
   - 변환 내역에서 여러 개 선택 → [GitHub로] [Obsidian으로] [둘 다] 버튼
   - 설정 옵션: "변환 완료 시 자동 내보내기" (대상 선택, 기본 OFF)
   - 내보내기 결과를 frontmatter exported 값과 내역 배지에 반영, 내보내기 이력 기록

5. 테스트: GitHub는 테스트용 임시 저장소 또는 모의(mock) 서버로, Obsidian은 임시 폴더로 자동 테스트

참고: 맥미니의 ~/LLM-wiki 로컬 사본은 별도 자동 동기화(15분 주기 pull/push)가 돌고 있어. API로 올린 커밋이 그 동기화와 충돌하지 않도록, 앱은 LLM-wiki의 inbox/markflow/ 폴더에만 쓰고 다른 경로는 건드리지 마.
```

**완료 기준**

## Phase 6. 클라우드 저장소 연결 — 가져오기(Source) + 저장(Destination)

**목적:** Google Drive·OneDrive·Dropbox·iCloud Drive에 있는 파일을 바로 골라 변환하고, 변환 결과를 원하는 클라우드 폴더에 저장함

**연결 방식 (결정 사항)**
- 기본은 **동기화 폴더 방식**: 각 클라우드 앱(Google Drive for desktop, OneDrive, Dropbox, iCloud)을 PC에 깔면 생기는 폴더를 앱이 자동으로 찾아 일반 폴더처럼 씀
  · 장점: 4종 모두 동일하게 동작, 로그인·API 설정이 필요 없음, 비용 0원, 오프라인에서도 동작
  · iCloud는 공개 API가 없어 이 방식만 가능함
- 보조는 **API 방식(OAuth 로그인)**: 동기화 앱을 깔 수 없는 PC(예: 회사 노트북)용. Google Drive·OneDrive·Dropbox 3종만 해당
  ※ 회사 M365 계정의 OneDrive는 회사 관리자 승인 없이는 API 로그인이 막힐 수 있음 → 회사 노트북에서는 이미 설치된 OneDrive 동기화 폴더 방식을 우선 사용

```
[Phase 6 — 클라우드 저장소 연결]

markflow-rules.md 5-1장(클라우드 저장소 연결 원칙)을 따른다.

1. 저장소 어댑터(StorageAdapter) 공통 구조
   - 인터페이스: list(폴더 목록), read(로컬 임시폴더로 내려받기), write(파일 쓰기), exists, watch(가능한 경우)
   - 구현체: LocalFolderAdapter(동기화 폴더 4종 공용), GoogleDriveApiAdapter, OneDriveGraphAdapter, DropboxApiAdapter
   - Phase 5의 Obsidian 내보내기와 Library 저장도 같은 인터페이스로 정리해서 "저장 대상"을 하나의 개념으로 통일해

2. 동기화 폴더 자동 감지 (mac / Windows)
   - Google Drive: mac `~/Library/CloudStorage/GoogleDrive-<계정>/` 아래 "내 드라이브(My Drive)", Windows 가상 드라이브(보통 G:)의 "내 드라이브"
   - OneDrive: mac `~/Library/CloudStorage/OneDrive-*`, Windows 환경변수 OneDrive / OneDriveConsumer / OneDriveCommercial
   - Dropbox: Dropbox의 info.json(mac `~/.dropbox/info.json`, Windows `%APPDATA%\Dropbox\info.json` 또는 `%LOCALAPPDATA%\Dropbox\info.json`)에서 경로 읽기, 없으면 `~/Library/CloudStorage/Dropbox`·`%USERPROFILE%\Dropbox` 확인
   - iCloud Drive: mac `~/Library/Mobile Documents/com~apple~CloudDocs`, Windows `%USERPROFILE%\iCloudDrive`
   - 위 경로는 출발점일 뿐이니, 실제 OS·앱 버전에서 경로가 맞는지 확인하고 못 찾으면 사용자가 폴더를 직접 고를 수 있게 해
   - 계정이 여러 개면(예: 개인 Google + 회사 OneDrive) 모두 나열

3. 온라인 전용 파일 처리
   - 클라우드에만 있고 PC에 내려받지 않은 파일(구름 아이콘, iCloud `.icloud` 자리표시 파일)을 감지
   - 변환 전에 내려받기를 시작하고, 완료될 때까지 대기열 상태를 "내려받는 중"으로 표시. 시간 초과(예: 2분) 시 "다운로드 실패"로 안내
   - OS별 내려받기 방법은 추측하지 말고 확인한 뒤 구현해

4. API 방식 (보조) — OAuth 2.0 + PKCE, 127.0.0.1 루프백 리다이렉트, 시스템 기본 브라우저로 로그인
   - Google Drive API: 원본 찾아보기용 읽기 권한 + 저장용 쓰기 권한. 권한 범위(scope)는 최소로 하고, 각 scope가 왜 필요한지 docs/cloud-oauth.md에 기록
   - Microsoft Graph(OneDrive): 개인 Microsoft 계정 기준. 회사 계정은 관리자 승인이 필요할 수 있다고 화면에 안내
   - Dropbox API: App folder가 아닌 Full Dropbox 접근이 필요한지 판단해서 계획에 적어
   - 토큰(액세스·리프레시)은 safeStorage에만 저장, 만료 시 자동 갱신, [연결 해제] 시 토큰 삭제
   - 각 서비스의 개발자 콘솔에서 내가 직접 앱(Client ID)을 등록해야 하니, 등록 절차를 비개발자용으로 docs/cloud-oauth.md에 클릭 순서대로 써줘 (모두 무료 범위로)
   - Google OAuth 앱은 "테스트" 상태로 두고 내 계정(테스트 사용자)만 쓰는 방식으로 — 공개 앱 심사가 필요 없게
   - 큰 파일은 서비스별 이어올리기(resumable/chunked upload) 사용

5. 화면
   - 왼쪽 "변환 대기열" 위에 탭: [내 PC] [클라우드]
     · [클라우드] 탭: 연결된 저장소 목록(아이콘 + 계정명) → 폴더 탐색기(트리 + 파일 목록, 지원 형식만 강조) → 파일·폴더 체크 후 [대기열에 추가]
     · 클라우드 원본의 frontmatter에는 source_file 외에 source_location(예: "Google Drive:/업무/보고서.pptx") 기록
   - "저장 대상" 설정 (설정 > 저장 대상)
     · 기본 저장 위치: Library(로컬)
     · 추가 저장 대상 여러 개 등록 가능: 각 클라우드의 특정 폴더 지정
     · 저장 폴더 규칙(템플릿): 예) `MarkFlow/{yyyy}/{mm}/` 또는 `{원본폴더 구조 유지}`
     · "변환 완료 시 자동 저장" 토글 (대상별)
   - 변환 내역에서 여러 개 선택 → [저장 대상으로 보내기] 메뉴에 등록한 클라우드 폴더가 나오도록. Phase 5의 [GitHub로] [Obsidian으로]와 같은 줄에 배치
   - 내보내기 배지에 클라우드 저장 여부 표시, frontmatter exported에 { gdrive, onedrive, dropbox, icloud } 추가

6. 감시 폴더 자동 변환 (Watch Folder)
   - 로컬·클라우드 동기화 폴더 중 원하는 폴더를 "감시 폴더"로 지정 → 새 파일이 들어오면 자동으로 대기열 추가 및 변환
   - 이미 변환한 파일은 파일 해시로 판별해 중복 변환하지 않음. 원본이 수정되면 "원본 변경됨" 표시 후 재변환 여부를 물어봄
   - 동기화 중인 반쯤 내려받은 파일을 변환하지 않도록, 파일 크기가 일정 시간(예: 5초) 변하지 않을 때만 처리

7. 안전장치
   - 원본은 읽기 전용. 어떤 경우에도 원본 파일을 수정·이동·삭제하지 않음
   - 같은 이름 파일이 저장 대상에 있으면 Phase 5와 같은 [덮어쓰기 · 이름 바꿔 저장 · 건너뛰기] 선택
   - 동기화 충돌 파일(예: "conflicted copy", "(1)" 붙은 사본)을 감지하면 보드와 내역에서 경고
   - 저장 대상이 클라우드 폴더여도 SQLite DB는 절대 그쪽에 두지 않음

8. 테스트
   - 감지 로직: 각 OS의 가짜 폴더 구조·환경변수를 만들어 단위 테스트
   - API 어댑터: 모의(mock) 서버로 목록·내려받기·올리기·토큰 갱신 테스트
   - 실제 확인: 맥미니에서 iCloud Drive·Google Drive 동기화 폴더 기준 왕복(가져오기 → 변환 → 저장) 테스트 결과를 walkthrough에 스크린샷으로

Implementation Plan에 (1) 4개 클라우드별 지원 방식 표(동기화 폴더/API, 가져오기/저장, 제약) (2) 내가 직접 해야 할 준비 작업 목록을 먼저 보여줘.
```

**완료 기준**
- [클라우드] 탭에 PC에 설치된 클라우드 폴더가 자동으로 나타나고, Google Drive의 PPTX를 골라 변환할 수 있음
- 변환 결과가 지정한 iCloud Drive 폴더(또는 Dropbox 폴더)에 저장되고, 아이폰 파일 앱에서 보임
- 감시 폴더에 PDF를 넣으면 손대지 않아도 변환 내역에 새 항목이 생김
- 원본 파일의 수정 시각이 변환 전후로 바뀌지 않음

## Phase 7. 노션형 보드 (MD 파일 기반 문서 관리)

**목적:** 변환된 MD 파일들을 노션 데이터베이스처럼 표·칸반·갤러리로 관리함. 데이터는 항상 MD 파일 자체에 있음(앱을 지워도 파일은 남음)

```
[Phase 7 — 노션형 보드]

원칙: 원본 데이터는 Library 폴더의 MD 파일과 frontmatter. SQLite는 빠른 조회용 색인일 뿐이며, 언제든 MD 파일로부터 다시 만들 수 있어야 해.

1. 별도 탭을 만들지 말고 사이드바 [라이브러리]·영역/프로젝트·태그 화면에 보드 기능을 넣어. 본문 오른쪽 위 작은 전환 버튼으로 보기 변경, 기본 보기는 Things처럼 깔끔한 목록
2. 보드 기능
   - 보기 4종: 목록(기본) · 표(Table) · 칸반(Kanban, status 기준 열) · 갤러리(첫 이미지 썸네일 + 제목)
   - 속성: frontmatter 기반 — title, status, tags, groups, category, source_type, converted_at, quality_score, exported
   - 사용자 정의 속성 추가 가능(텍스트·선택·다중선택·날짜·체크박스) → frontmatter에 기록
   - 필터·정렬·그룹(예: category별 그룹), 보기 설정 저장 (보기 이름 지정)
   - 칸반에서 카드 드래그로 status 변경 → 즉시 MD frontmatter 갱신
   - 표에서 셀 직접 편집
   - 전문 검색: SQLite FTS5로 제목+본문 검색, 한국어 검색이 되도록 토크나이저 설정(trigram 등) 검토
   - 새 문서 만들기(빈 MD), 문서 복제, 보관(status=보관, 기본 보기에서 숨김)
   - 문서 클릭 → Phase 4 상세 화면
3. 동기화
   - Library 폴더를 감시(chokidar)해서 앱 밖(예: 다른 편집기)에서 MD를 고쳐도 보드에 반영
   - 앱 시작 시 색인 재검사, [색인 다시 만들기] 버튼
4. 일괄 작업: 여러 문서 선택 → 태그 추가/상태 변경/내보내기/삭제
5. 테스트: frontmatter 읽기·쓰기 왕복 시 본문과 다른 속성이 손상되지 않는지 pytest/vitest로 검증 (한글·특수문자 포함)
```

**완료 기준**
- 칸반에서 카드를 "완료" 열로 옮긴 뒤 MD 파일을 텍스트 편집기로 열어보면 `status: 완료`로 바뀌어 있음
- Obsidian에서 고친 내용이 아니라 Library 폴더에서 직접 고친 내용이 보드에 자동 반영됨

## Phase 8. 개인 지식 관리(PKM) 고도화 — DEVONthink형 기능

**목적:** 단순 변환기를 넘어, 모은 문서를 자동으로 분류·연결·검색하는 종합 문서·지식 관리 앱으로 완성함

**핵심 개념 (쉬운 설명)**
- 그룹: 문서를 묶는 폴더 같은 것. 단, 실제 파일은 한곳(Library)에 두고 frontmatter의 `groups` 값으로 묶음 → 한 문서를 여러 프로젝트에 동시에 넣을 수 있음(DEVONthink의 "복제본" 개념)
- 스마트 그룹: "태그가 '보고서'이고 최근 30일 문서"처럼 조건을 저장해 두면 자동으로 채워지는 그룹
- 관련 문서 추천: 문서 내용의 "의미"를 숫자로 바꾼 값(임베딩)을 비교해 비슷한 문서를 찾아줌. 내 PC 안에서만 계산(무료·외부 전송 없음)

```
[Phase 8 — PKM 고도화]

markflow-rules.md 8장(UI 원칙)을 지키면서, 기능이 늘어도 화면이 복잡해지지 않게 해. 새 기능은 대부분 "문서 오른쪽 정보 패널"과 "사이드바 항목"으로만 노출해.

1. 그룹 체계 (영역 > 프로젝트)
   - 사이드바에서 영역·프로젝트 생성·이름변경·순서변경(드래그)
   - frontmatter `groups: [영역/프로젝트]` 로 기록. 한 문서가 여러 그룹에 속할 수 있음
   - 문서를 사이드바 프로젝트로 드래그하면 그룹 추가, Alt(Option)+드래그는 이동

2. 스마트 그룹 · 고급 검색
   - 검색 문법: 띄어쓰기=AND, OR, -제외, "정확한 구문", 필드검색(tag:보고서, type:pdf, status:검토중, group:AX, date:>2026-09-01)
   - 검색 결과를 [스마트 그룹으로 저장] → 사이드바에 표시, 실시간 갱신
   - 기본 스마트 그룹: "검토 필요"(품질 70점 미만), "이번 주 추가", "내보내지 않음"

3. 자동 분류 제안 · 관련 문서 (로컬 AI, 비용 0원)
   - 엔진에 로컬 임베딩 모델 추가(한국어 지원 다국어 소형 모델, ONNX 기반으로 CPU에서 동작) — 모델 후보 2~3개를 비교해 한국어 품질과 속도로 1개 선정, 근거를 docs/adr/에 기록
   - 벡터 저장은 SQLite 확장(sqlite-vec)으로 같은 DB에
   - 문서 정보 패널에 "관련 문서" 5개 표시
   - 수집함 문서마다 "추천 프로젝트·태그" 칩 표시 → 클릭 한 번으로 적용 (DEVONthink의 분류 제안처럼)
   - 처음 실행 시 모델 내려받기 진행률 표시, 이후 오프라인 동작

4. 위키 링크 · 백링크
   - 편집기에서 `[[` 입력 시 문서 제목 자동완성 → Obsidian과 같은 `[[문서 제목]]` 형식으로 저장 (Obsidian 내보내기 시 그대로 호환)
   - 정보 패널에 "이 문서를 가리키는 문서(백링크)" 목록
   - 제목 변경 시 다른 문서의 링크도 자동 갱신 (되돌리기 가능)

5. 하이라이트 · 메모
   - 미리보기에서 문장 선택 → [하이라이트] [메모] 떠 있는 버튼
   - 저장 형식: `==하이라이트==` (Obsidian 호환), 메모는 각주 형식
   - 사이드바 [하이라이트 모음] 화면: 모든 문서의 하이라이트를 한곳에서 보기

6. 중복 탐지
   - 같은 파일(해시 동일)은 가져올 때 "이미 있음" 안내
   - 내용이 거의 같은 문서(임베딩 유사도 높음)는 정보 패널에 "비슷한 문서 있음" 표시 → [합치기] [둘 다 유지]

7. 스마트 규칙 (자동화)
   - "조건 → 동작" 규칙을 문장처럼 만드는 화면: 예) "원본이 Google Drive:/업무 폴더이고 형식이 pptx이면 → 프로젝트 'AX'에 넣고 태그 '발표자료' 붙이고 GitHub로 내보내기"
   - 실행 시점: 변환 완료 시 / 매일 정해진 시각 / 수동
   - 규칙 실행 기록은 [기록] 화면에 남김

8. 인덱싱(색인) vs 가져오기
   - 가져오기: 파일을 변환해 Library에 MD로 보관 (지금까지의 방식)
   - 인덱싱: 클라우드·로컬 폴더를 복사하지 않고 "목록과 검색 색인만" 만들어 라이브러리에서 함께 검색 (Phase 6 어댑터 재사용). 필요할 때 [가져오기]로 MD 변환
   - 인덱싱 항목은 목록에서 연한 회색 아이콘으로 구분

9. 빠른 입력 (Quick Entry) · 웹 수집
   - 전역 단축키(기본 Ctrl+Shift+Space, mac은 Cmd 대신 Ctrl — 다른 앱과 충돌 시 설정에서 변경)로 작은 창 호출
   - 입력 가능: 파일 드롭, URL 붙여넣기(웹페이지를 내려받아 HTML 전처리 → MD 변환), 짧은 메모
   - 입력 즉시 창이 닫히고 수집함에 들어감. 메뉴바(mac)/트레이(Windows) 아이콘에서도 호출

10. 오늘(Today) · 기록(Logbook)
   - 오늘: 사용자가 "오늘 볼 문서"로 표시한 문서 + 오늘 변환된 문서 + 검토 필요 문서
   - 기록: 변환·내보내기·규칙 실행·삭제 이력을 날짜별로. 각 항목에서 되돌리기 가능한 것은 되돌리기

11. 테스트
   - 검색 문법 파서, 스마트 그룹 조건, 규칙 엔진은 단위 테스트
   - 임베딩: 골든셋에 "서로 관련 있는 문서 쌍"을 정의하고 관련 문서 상위 5개 안에 들어오는지 검사
   - 문서 1,000개 기준 검색 응답 0.3초 이내, 관련 문서 계산 1초 이내

Implementation Plan에서 기능 10개를 한 번에 만들지 말고 (가) 1·2·10 (나) 4·5 (다) 3·6 (라) 7·8·9 네 묶음으로 나눠, 묶음마다 승인받고 진행해.
```

**완료 기준**
- 수집함에 새로 들어온 문서에 "추천 프로젝트·태그" 칩이 뜨고, 클릭 한 번으로 분류됨
- `tag:보고서 date:>2026-10-01` 검색을 스마트 그룹으로 저장하면 사이드바에 생기고 자동 갱신됨
- 다른 앱을 쓰다가 단축키로 URL을 붙여넣으면 잠시 후 수집함에 MD 문서로 들어옴
- 이 모든 기능이 들어가도 첫 화면이 사이드바 + 목록 두 영역으로 유지됨

```
3. PyInstaller는 OS별로 따로 빌드해야 하므로 GitHub Actions 매트릭스(macos-latest, windows-latest)로 태그(v*) 푸시 시 양쪽 설치 파일을 만들어 GitHub Releases(비공개 저장소)에 첨부
4. 코드 서명은 하지 않음(비용 발생). 대신 docs/install-guide.md에 비개발자용 설치 안내 작성
   - mac: "확인되지 않은 개발자" 경고 시 우클릭 → 열기 (또는 시스템 설정 > 개인정보 보호 및 보안 > 그래도 열기)
   - win: SmartScreen 경고 시 "추가 정보 → 실행"
   - 회사 노트북은 보안 정책상 설치가 막힐 수 있으니 IT 정책 확인 필요하다는 점 명시
5. 앱 아이콘(간단한 원본 디자인), 앱 이름·버전 표시
6. 릴리스 노트 자동 생성
```

**완료 기준**
- GitHub Releases에 `.dmg`, `.exe`가 올라오고, 각각 다른 PC에 설치해 `samples/` 변환 → 클라우드 폴더 저장 → Obsidian 내보내기까지 동작함
